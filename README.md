# My NixOS configuration

A flake-based NixOS and Home Manager configuration for multiple machines. The current configurations are `laptop` and `desktop`; host-specific system and Home Manager files live under `hosts/`, while reusable modules live under `modules/`.

> **This is a personal configuration, not a turnkey installer.** Review the hardware, storage, user, network, and secret settings before using it on another machine. In particular, the current flake defaults to user `monavixx`, home/flake path `/home/monavixx/nixos`, and `x86_64-linux`. Host hardware files contain machine-specific disk identifiers.

## How the configuration is organized

- `flake.nix` declares inputs and exports `nixosConfigurations` for `laptop` and `desktop` through `mkHost`.
- `hosts/<hostname>/configuration.nix` contains host-specific NixOS settings and imports that host's `hardware-configuration.nix`.
- `hosts/<hostname>/home.nix` selects the Home Manager configuration for the host.
- `modules/nixos/` and `modules/home-manager/` contain reusable modules. The current common Home Manager module imports most of the personal desktop environment and applications.
- `secrets/agenix-rules.nix` maps encrypted secrets to SSH public-key recipients. Secret values are stored in `.age` files.
- `flake.lock` pins the inputs. Keep it under version control so machines build from the same revisions.

The `nixosConfigurations` attribute name is the install/rebuild target (`laptop` or `desktop`). The `networking.hostName` value is passed from the host configuration in `flake.nix` and should match the machine's intended hostname.

## Install on an existing host

On a running NixOS system with Git available, clone the repository to the location expected by this configuration. The current default `flakeRoot` is `/home/monavixx/nixos`:

```sh
mkdir -p ~/nixos
# Clone into ~/nixos (or use your existing checkout there).
git clone https://github.com/Monavixx/my-nixos-config.git ~/nixos
cd ~/nixos
```

If the directory already contains a checkout, update it instead:

```sh
cd ~/nixos
git pull --ff-only
```

Build first to check evaluation, then activate the selected configuration:

```sh
sudo nixos-rebuild build --flake .#laptop
sudo nixos-rebuild switch --flake .#laptop
```

Replace `laptop` with `desktop` or the new configuration's flake output name. For a remote checkout, use its absolute path or a flake reference instead of `.`. A successful `switch` activates the new system and normally does not require a separate imperative step.

## Install on a new device

### Before installation

1. Install NixOS using the official installer and prepare/mount the target filesystems. The generated hardware configuration must describe the target device's actual disks, filesystems, boot method, and platform.
2. Decide the target's hostname, Linux username, architecture, and checkout path. The current `mkHost` defaults are `username = "monavixx"`, `flakeRoot = "/home/monavixx/nixos"`, and `system = "x86_64-linux"`; these are not automatically derived from the host name.
3. Add a host configuration as described below, and check that all imported modules and packages are appropriate for the device. Do not copy another machine's `hardware-configuration.nix` or disk UUIDs.
4. If the host should decrypt agenix secrets, prepare its SSH host key recipient and update the agenix rules as described in [Secrets and agenix](#secrets-and-agenix).

### Add a host

For a host named `new-host`:

1. Create `hosts/new-host/` with:
   - `configuration.nix` — imports shared system modules and the new host's hardware configuration, then adds host-specific settings.
   - `hardware-configuration.nix` — generate this on the target using `nixos-generate-config` (or retain the file generated by the installer), then review it carefully.
   - `home.nix` — imports the appropriate Home Manager modules and adds host-specific user settings.
2. Add a `new-host` entry to `outputs.nixosConfigurations` in `flake.nix`, using `mkHost`. Set the host values that differ from the defaults, at least `hostname`; also set `username`, `flakeRoot`, `system`, or `theme` where necessary. For a different username, make sure the `flakeRoot` is also correct: the current default path is explicitly `/home/monavixx/nixos`, not a path derived from an overridden username.
3. Check that the selected user is created by the NixOS modules and is the same user configured by Home Manager. The current flake attaches one Home Manager user (`host.username`) to each NixOS configuration; it does not yet configure multiple users on one host.
4. Review host-specific settings copied from other machines (GPU drivers, LUKS UUIDs, mount points, power settings, fingerprint reader, etc.). Remove or adapt settings that do not match the target.
5. From the repository root, evaluate/build the new output before installing:

   ```sh
   nix flake check
   nixos-rebuild build --flake .#new-host
   ```

   `nix flake check` checks flake outputs but is not a substitute for checking the target's hardware and boot setup.

### Build and install from the NixOS installer

Clone/copy the repository into a path available in the live installer and use the new output name. If the target's root filesystem is mounted at `/mnt`, one possible checkout location is `/mnt/home/<username>/nixos` (create the directory first):

```sh
sudo mkdir -p /mnt/home/<username>/nixos
sudo git clone https://github.com/Monavixx/my-nixos-config.git /mnt/home/<username>/nixos
sudo nixos-install --flake /mnt/home/<username>/nixos#new-host
```

Replace `<username>` and `new-host` with the values configured in the flake. Ensure the checkout is readable by the installer and that the configured `flakeRoot` points to the intended path once the system is installed. If you have already cloned the repository elsewhere in the live environment, use that checkout path instead. Follow the installer prompts, set the initial account password as required, then reboot into the installed system.

## After installation

Most system setup should be declarative. Avoid repeating a command-line change if it can be represented safely in Nix; imperative changes can be lost on rebuild or make machines drift.

### Required checks

- Log in and verify networking, storage mounts, boot, graphics, and the intended user account.
- Confirm the running host has the SSH key expected by agenix, if this machine needs to decrypt secrets. NixOS-generated SSH host keys are commonly under `/etc/ssh/`; do not publish or commit private keys.
- Rebuild after any first-boot hardware or configuration correction:

  ```sh
  cd ~/nixos
  sudo nixos-rebuild switch --flake .#new-host
  ```

### Optional, machine-dependent setup

These are examples, not mandatory steps for every machine:

- Pair Bluetooth devices or enroll fingerprints if the relevant hardware and services are enabled.
- Sign in to applications and configure accounts that cannot or should not be managed declaratively.
- Restore personal data from backup and mount any additional data drives after verifying their UUIDs and filesystem options.
- If you deliberately use a different checkout path, update `flakeRoot` and Home Manager's `nh` configuration to match.

Do not run commands that format disks or recreate encryption unless you are intentionally provisioning storage and have verified the target device and backup. Disk layout and encryption are machine-specific.

## Regular operations

Run flake commands from the repository root unless noted otherwise.

### Test and apply configuration changes

```sh
nix flake check
sudo nixos-rebuild build --flake .#laptop
sudo nixos-rebuild switch --flake .#laptop
```

Replace `laptop` with the desired flake output. To test without activating, use `build`; to activate and make it the current system, use `switch`. Consider booting into a new generation before removing older generations.

The configuration also includes `nh` and a custom `rebuild` command. The custom command currently changes to `~/nixos`, runs `git add .`, and rebuilds the current host. Be aware that it stages every change in that checkout; inspect the script before using it if you do not want that behavior. The explicit `nixos-rebuild` commands above avoid staging files.

### Update inputs

```sh
nix flake update
nix flake check
sudo nixos-rebuild build --flake .#laptop
```

Review the `flake.lock` diff and test the build before switching. To update a single input, use `nix flake lock --update-input <input-name>`.

### Secrets and agenix

The agenix rules file is `secrets/agenix-rules.nix`. The examples below pass it explicitly so the commands use this repository's rules.

Edit or create an encrypted secret from the repository root:

```sh
agenix -r secrets/agenix-rules.nix -e secrets/<secret-name>.age
```

After changing recipients in `secrets/agenix-rules.nix`, re-encrypt the configured secret files for the new recipient set:

```sh
agenix -r secrets/agenix-rules.nix --rekey
```

Check the agenix version's `agenix --help` if the command-line options differ in your installation. Never commit plaintext secret material, private SSH keys, or decrypted secret files. Commit only the encrypted `.age` files and the public recipient/rules changes.

To add a device that needs to decrypt secrets:

1. Obtain its **public** SSH key. For a host key this is typically `/etc/ssh/ssh_host_ed25519_key.pub`; for a user recipient, use the intended user's public key. The matching private key must remain secret and available on the recipient machine.
2. Add the public key to `secrets/agenix-rules.nix` and include it in the recipient list for each secret that machine/user needs.
3. Run the rekey command above, review the encrypted-file changes, and commit/push the rules and re-encrypted `.age` files.
4. Pull the updated repository on the recipient and rebuild so the encrypted secrets can be activated.

A recipient's public key only grants access to secrets after they are rekeyed for that recipient. Protect the private key and have a recovery plan for secrets before removing old recipients.

## Ideas for scaling the configuration

The current `mkHost` helper is a useful start. The next improvements can be incremental; there is no need to add an abstraction for every setting.

- **Make host data explicit and validated.** Keep a host inventory (or a small attribute set in the flake) containing hostname, system architecture, users, theme, and optional feature profiles. Avoid relying on implicit defaults for values that change per person or device. Add assertions for required fields and unknown host names.
- **Separate hosts, users, and roles.** Keep hardware and machine-only services in `hosts/<host>/`; put reusable per-person Home Manager settings under `users/<user>/`; and use opt-in profiles such as `desktop`, `laptop`, `gaming`, or `server` for capability-based bundles. This makes multiuser hosts possible without duplicating whole Home Manager configurations.
- **Split the current “common” modules by purpose.** `modules/nixos/common.nix` currently enables a graphical/desktop-oriented stack (including Hyprland, PipeWire, DNS, and desktop portals), and the common Home Manager module imports many personal desktop applications. Separate a small base from optional desktop, laptop, audio, development, and server profiles so a new device only opts into what it needs.
- **Derive paths from the selected user.** The current flake's `flakeRoot` default is hard-coded to `/home/monavixx/nixos`, while the rebuild script changes to `~/nixos`. Use one source of truth and derive the home path where appropriate; avoid assumptions that break for another username or a nonstandard home directory.
- **Make user and host creation data-driven.** The current output maps each host to one `host.username` Home Manager user. If multiple users per host are a goal, make the user map explicit and instantiate Home Manager for each account, with per-user imports and options.
- **Keep hardware-specific state isolated.** Preserve generated hardware configuration per host and keep disk IDs, boot settings, GPU drivers, and device-specific services out of general shared modules. Consider a documented host template to make this boundary obvious.
- **Make operations safer and reproducible.** Avoid `git add .` inside a rebuild helper; use a read-only build/check step and let Git commits be deliberate. Add formatting/lint tooling (for example `nixfmt`), `nix flake check`, and a CI evaluation/build matrix for every flake configuration.
- **Document secret ownership and recovery.** Keep the recipient list and secret access needs understandable, rekey after recipient changes, and maintain a safe recovery recipient. Never store private keys or plaintext secrets in the repository.

A practical first refactor would be: correct the `flakeRoot` default/path handling, split generic base settings from a desktop profile, then move user settings out of host-specific Home Manager files. That improves reuse without making the flake unnecessarily abstract.
